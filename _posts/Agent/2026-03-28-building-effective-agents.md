## 一、基本概念

### 什么是智能体系统？

| 类型 | 定义 | 特点 |
|------|------|------|
| **工作流（Workflow）** | LLM 按预定义代码路径执行 | 可预测、一致性强 |
| **智能体（Agent）** | LLM 动态规划并自主调用工具 | 灵活、自主决策 |

两者统称为**智能体系统（Agentic Systems）**。

---

## 二、何时使用智能体？

**首要原则：从最简单的方案开始，只在必要时增加复杂度。**

```
单次 LLM 调用（优化 prompt）
    ↓ 不够时
工作流（Workflow）
    ↓ 不够时
智能体（Agent）
```

- 智能体系统以**更高延迟和成本**换取**更强的任务处理能力**
- 很多场景下，优化单次 LLM 调用 + 检索增强（RAG）已足够

---

## 三、关于框架的建议

常见框架：Claude Agent SDK、Strands Agents SDK、Rivet、Vellum 等。

**建议：**
- ✅ 优先直接调用 LLM API，大多数模式几十行代码即可实现
- ✅ 使用框架前，确保理解其底层实现
- ⚠️ 框架的抽象层会掩盖 prompt 和响应，增加调试难度

## 四、核心构建模块

### 4.0 基础：增强型 LLM

所有智能体系统的基础单元：**LLM + 检索 + 工具调用 + 记忆**

```
用户输入 → [增强型 LLM] → 输出
              ↑
         检索 / 工具 / 记忆
```

---

### 4.1 工作流：提示链（Prompt Chaining）

将任务分解为顺序步骤，每步的输出作为下一步的输入，中间可插入校验逻辑。

```
输入 → LLM₁ → [校验] → LLM₂ → [校验] → LLM₃ → 输出
```

**适用场景：**
- 任务可清晰分解为固定子步骤
- 追求更高准确率，可接受更长延迟

**示例：**
- 先生成营销文案 → 再翻译成目标语言
- 先写大纲 → 校验大纲 → 再写正文

---

### 4.2 工作流：路由（Routing）

先对输入分类，再将其导向对应的专属处理流程。

```
输入 → [分类器] → 类型A → 专属流程A
                 → 类型B → 专属流程B
                 → 类型C → 专属流程C
```

**适用场景：**
- 输入类别明确且差异较大
- 各类别处理逻辑互不干扰

**示例：**
- 客服系统：将退款/技术支持/一般咨询分别路由到不同流程
- 按问题难度路由：简单问题 → 小模型（省成本），复杂问题 → 大模型（保质量）

---

### 4.3 工作流：并行化（Parallelization）

多个 LLM 实例同时处理任务，最后汇总结果。

```
              ┌→ LLM₁ ─┐
输入 → [分发] ├→ LLM₂ ─┤→ [聚合] → 输出
              └→ LLM₃ ─┘
```

**两种变体：**

| 变体 | 说明 | 示例 |
|------|------|------|
| **分段（Sectioning）** | 将任务拆分为独立子任务并行执行 | 内容审核与正常回复同时进行 |
| **投票（Voting）** | 同一任务多次运行，取共识结果 | 多角度代码漏洞扫描 |

**适用场景：** 子任务相互独立、需要多角度验证时。

---

### 4.4 工作流：编排者-工作者（Orchestrator-Workers）

一个主 LLM 动态分解任务，分配给多个工作 LLM，最后汇总。

```
             ┌→ Worker₁ ─┐
输入 → [编排者] ├→ Worker₂ ─┤→ [汇总] → 输出
             └→ Worker₃ ─┘
     （动态决定任务拆分方式）
```

**与并行化的区别：** 并行化的子任务是预定义的；编排者模式的子任务由 LLM 根据具体输入动态生成。

**适用场景：**
- 无法事先预知需要哪些子任务
- 编程类任务（需修改的文件数量和内容因需求而异）
- 多源信息搜集与分析

---

### 4.5 工作流：评估者-优化者（Evaluator-Optimizer）

一个 LLM 生成结果，另一个 LLM 评估并反馈，形成迭代优化循环。

```
输入 → [生成者] → 初稿
              ↑         ↓
         修改建议  [评估者]
              ↑         ↓
              └── 反馈 ──┘  （直到满足标准）→ 输出
```

**适用场景：**
- 有明确的评估标准
- 迭代改进能带来可衡量的提升

**示例：**
- 文学翻译：评估者指出细节缺失，生成者重新翻译
- 复杂信息检索：评估者判断是否需要继续搜索

---

### 4.6 自主智能体（Agent）

LLM 在环境反馈中循环调用工具，自主完成开放式任务。

```
输入/指令 → [LLM] → 工具调用
                 ↑         ↓
            环境反馈  工具执行结果
                 ↑         ↓
                 └──────────┘  → （任务完成或达停止条件）
```

**适用场景：**
- 任务步骤数量无法预先确定
- 需要复杂推理和动态决策

**注意事项：**
- 自主性越高，成本越高，错误累积风险也越大
- 建议在沙盒环境中充分测试，并设置合理的终止条件和护栏

**成功案例：**
- SWE-bench 代码问题修复 Agent
- Claude Computer Use 计算机操控 Agent

## 五、实际应用场景

### 客户支持

**天然适合智能体的原因：**
- 对话流 + 工具调用（查订单、调知识库）天然结合
- 操作可程序化（退款、更新工单）
- 成功与否可量化衡量

### 代码智能体

**天然适合智能体的原因：**
- 代码可通过测试自动验证
- 测试结果可作为迭代反馈
- 问题空间结构清晰，质量可客观度量

---

## 六、工具设计最佳实践

工具文档需要像 prompt 一样精心设计，可理解为**智能体-计算机接口（ACI）**。

**设计原则：**

1. **站在模型角度审视**：工具描述是否清晰？参数是否直观？
2. **写好文档**：包含用途说明、参数说明、示例用法、边界情况
3. **实测验证**：在 workbench 中用大量真实输入测试，观察模型的实际使用行为
4. **防错设计（Poka-yoke）**：修改参数设计，让错误更难发生

**格式选择建议：**
- 给模型足够的 token "思考空间"
- 选择接近自然语言语料的格式（如 Markdown 优于 JSON 转义代码）
- 避免需要维护精确计数或复杂转义的格式

> 💡 **实践经验**：Anthropic 在构建 SWE-bench Agent 时，花在工具优化上的时间超过了 prompt 优化。例如，将文件路径参数从相对路径改为绝对路径，彻底解决了路径错误问题。

---

## 七、三条核心原则

1. **保持简洁（Simplicity）**：智能体设计不要过度复杂
2. **透明可见（Transparency）**：明确展示智能体的规划步骤
3. **工具文档（Documentation）**：精心设计并测试每一个工具

---

## 总结

| 场景 | 推荐方案 |
|------|---------|
| 任务简单、可用单次调用解决 | 优化单次 LLM 调用 |
| 任务可分解为固定步骤 | 工作流（提示链/路由/并行化） |
| 任务复杂、步骤不可预知 | 自主智能体 |

**核心思路：先用最简单的方案，只在简单方案确实不足时，才逐步引入复杂度。**
